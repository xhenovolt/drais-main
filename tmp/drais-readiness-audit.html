Production Reliability Audit · Evidence-based

Can a school depend on DRAIS for twelve months without you?

Every finding below was measured against the live production database and the current main tree. No claim rests on documentation, comments, or prior reports.

Commit 674a09d3 Version 1.173.29 Schema 294 tables Schools 23 (17 with modules) Date 2026-08-10
Verdict · Yes, with hardening

The architecture is sound. Four specific defects stand between it and a year of autonomy.

The things that are hardest to retrofit — multi-tenant isolation, attendance ingestion, soft-delete recovery, audit logging — are genuinely built and working in production. That is the expensive part, and it is done.

What is missing is not architecture but enforcement and housekeeping: an unenforced login lockout, a client-writable role cookie, payments that are not atomic, and log tables growing without bound. All four are patch-or-minor work, none require redesign.

One scoped exception: Finance is enabled for all 18 schools but has 4 recorded payments in its entire history. It has never been load-bearing. If a school begins relying on it for a full academic year, the transaction and reconciliation gaps below become blocking. Attendance and Academics can carry a year today; Finance cannot yet.

01

How this was measured

Three instruments, all reproducible:

  • Schema diff. Extracted all 291 distinct table names referenced in SQL across src/ and diffed against information_schema on the live database.
  • Static audit of 692 API routes for session derivation, permission checks, transaction boundaries, and SQL interpolation.
  • Direct production queries for row counts, constraint coverage, index coverage, and module enablement.

Read-only throughout. Nothing was modified during the audit.

04

Security

P1  School login has no brute-force protection

/api/auth/login increments failed_login_attempts on every failure and resets it on success — but never reads it. The only status check is for an already-locked account, and nothing in the codebase sets that status from attempt count. Password guessing against a school account is unlimited and unthrottled.

The Control Center, by contrast, has a proper throttle in src/lib/control/login-guard.ts with a windowed backoff. The protection exists; it was never applied to the surface that 34 active users log in through.

P1  The role cookie is client-writable, and 13 admin routes rely on it

Middleware gates /admin/users, /finance, /api/admin and /api/finance on the drais_role cookie — which login sets with httpOnly: false so the middleware can read it. Anything the browser can read, the browser can rewrite.

That is survivable where the route re-checks permissions server-side. Finance does: 51 of 56 routes call requirePermission. Admin does not — 30 of 62 routes skip it, and 13 of those expose write methods:

admin/users/route.ts GET POST admin/users/[id]/route.ts PATCH DELETE admin/permissions/sync/route.ts POST GET admin/classes/[id]/teacher/route.ts GET POST admin/school-hours/route.ts GET PUT DELETE admin/staff/[id]/employment/route.ts GET POST

A Teacher or Receptionist who edits one cookie value reaches user creation, user deletion, and permission sync. Tenant isolation still holds — every one of these derives school_id from the session, so this is privilege escalation within a school, not across schools. That is what keeps it P1 rather than P0.

Holds up well
  • Password hashing: bcrypt $2b$12 for 38 of 39 users, one legacy $2a$10.
  • Session cookie: httpOnly, secure in production, sameSite: lax.
  • SQL injection: no user input reaches a query unparameterised. All 55 interpolation sites splice either allow-listed fragments or integers clamped through Math.min/Math.max(parseInt(...)).
  • Platform API: bearer auth with its own rate limiter.
Open, lower severity
  • P2 No CSRF token anywhere. Mitigated by sameSite: lax, which blocks the cross-site POST case in current browsers.
  • P2 Audit logging covers 67 of 692 routes (~10%). Deletions and finance are covered; most configuration changes are not.
  • P3 One legacy bcrypt cost factor to upgrade on next login.

06

Data integrity

Must fix  Payments are not atomic

43 of 692 routes open a transaction. In Finance it is 6 of 56. Recording a payment writes to finance_payments, student_ledger, and updates student_fee_items.paid / .balance. Without a transaction boundary, a failure between those writes leaves a payment recorded with a balance not reduced, or the reverse.

This has not yet caused damage because only 4 payments exist. It becomes near-certain within a term of real use.

Referential integrity

42 foreign keys across 294 tables. Integrity is almost entirely application-enforced. The system is already showing the consequence:

school 12004 (Jinja Progressive) students 0 enrolments 109 ← orphaned

109 active enrolments referencing students that are deleted or absent. Any class list or report for that school under-reports today.

Recovery works

1,469 of 6,124 students are soft-deleted and restorable — 24% of the table. /admin/trash and the restore endpoints are real and exercised. 45 tables carry deleted_at.

The caveat: only 45 of 294 tables have soft delete, so deletion in the other 249 is permanent. Audit log is active with 8,174 rows, most recent yesterday.

Should fix  Soft-delete filters are omitted in places

Measured directly: 14 of 279 staff rows are soft-deleted, and until this week none of the six staff-payroll analytics queries filtered deleted_at. That class of omission is invisible in review and shows up as two numbers on the same screen disagreeing. A codebase-wide sweep is warranted, not just the routes already found.

Attendance — the one-year test

Attendance is the most production-critical module and the most mature. It survives the founder test with two named gaps.

Records evaluated15,262present 8,262 · late 2,571 · absent 2,477
Raw events preserved13,914raw punches retained independently of evaluation
Unmatched punches6044.3% credited to nobody
Pending device users297awaiting identity mapping

What works without you: raw punches are preserved separately from evaluation, so a mapping error is recoverable rather than destructive. Clock drift is handled — punch_at records the true server instant while dedup uses device-reported time, and there are 18 recorded clock corrections and 5 time baselines in production. Recovery UI exists at /attendance/biometric/unassigned, /attendance/identity-matching, /attendance/time-health, and devices can be acquired and released from /admin/devices.

Two gaps that will need you

  • Attendance analytics reads dead tables. student_attendance and staff_attendance hold 0 rows; the engine writes attendance_records. The endpoint returns success with empty arrays, so it reads as "no data yet" rather than as a fault. 15,262 records are invisible to every analytics surface.
  • 604 unmatched punches have a UI but no workflow that drives an admin to it. Nothing surfaces the backlog on the dashboard, so it accumulates silently until someone asks why a learner's attendance is missing.
08

Finance — the one-year test

Finance has never been load-bearing, and its safety mechanisms are the least developed

student_fee_items 16,722 charges raised student_ledger 16,613 16,610 debits / 5 credits finance_payments 4 payments recorded, all schools, all time ledger 0 general ledger unused expenditures 0 no expense side exists fee_invoices 0 receipts 4

A ratio of 16,610 debits to 5 credits means schools have raised fees extensively and recorded essentially no receipts. Every finance report is therefore untested against real data — including the Income Statement and Balance Sheet fixes shipped this week, which have never had figures to be right or wrong about.

Present: fee structures, waivers, discounts, an adjustment endpoint (/api/finance/adjust), reversal affordances on the ledger and payments pages, and permission coverage at 51 of 56 routes — the best-governed area in the codebase.

Missing for a year of real use: transaction boundaries on payment writes (6 of 56 routes); no reconciliation screen; the general ledger and expenditure side unused, so no Income Statement can balance; and no maker-checker on payments despite finance.payments.record and .refund existing in the permission catalogue with no route consuming them.

09

Performance and scale

Architectural risk  Unbounded log growth with no retention job

These figures come from 3 devices across 2 active schools:

zk_parsed_logs 266,551 zk_device_logs 150,536 system_logs 54,476 zk_raw_logs 54,385 device_heartbeats 44,956 ───────── 570,904 rows of device telemetry

That is 37× the volume of the attendance records they produced. No retention or pruning job exists, and the cron that might have run one is not scheduled. At 50 schools with 3 devices each this is on the order of 28 million rows within a year, on tables that back operational screens.

Needs optimisation  Hot tables with no leading school_id index

student_ledger 16,613 rows no index leading on school_id people 7,130 rows no index leading on school_id staff 279 rows exams 175 rows

224 indexes across the schema do lead with school_id, so the pattern is understood — these are omissions, not a design choice. student_ledger and people are on the path of every fee and every name lookup; both become full scans as tenancy grows.

Must fix  Five cron routes exist and none of them run

vercel.json schedules: /api/result-deadlines ✓ daily 06:00 Present in code, never invoked: /api/cron/notification-drain /api/cron/device-status /api/cron/aggregate-refresh /api/cron/attendance-intelligence /api/cron/platform-webhooks

Notification delivery currently depends on device heartbeats opportunistically draining the outbox — which works only while a device is online. The outbox shows 8 messages stuck in sending. A school with no device, or a device offline overnight, has no message delivery at all.

Should fix — significant reliability gain

  • Repoint attendance analytics at attendance_records — 15,262 records currently invisible.
  • Repoint Inventory analytics at inventory_items / inventory_transactions; Requirements at requirements_master / student_requirements. Both are renames, not rebuilds.
  • Add indexes leading on school_id to student_ledger and people.
  • Surface the unmapped-punch backlog on the dashboard.
  • Codebase-wide deleted_at filter sweep.
  • Repair the 109 orphaned enrolments in school 12004 and add a constraint or check preventing recurrence.
  • Extend audit logging beyond 10% of routes to cover configuration changes.

Can wait

  • CSRF tokens — sameSite: lax covers the realistic case.
  • Foreign-key constraints — valuable, but retrofitting 294 tables is a major change, not a hardening pass.
  • Maker-checker on payments — matters once payment volume is real.
  • The one legacy bcrypt cost factor.

Safe to leave dormant

  • Parent portal — no data, no exposure, no dependency. Genuinely harmless.
  • Timetable and CAFE — provided they are removed from navigation. They need migrations and finishing work; there is no reason to invest unless a school asks. Leaving them visible is the problem, not leaving them unfinished.
  • Global search — absent index; the feature is not otherwise wired in.

13

The honest answer

Yes, with hardening — and the hardening is Phase 1, which is small.

Do not read this report as a long list of failures. Read the ratio: 411 of 416 routes correctly scoped, bcrypt at cost 12, raw attendance preserved independently of evaluation, 1,469 records recoverable through a working trash, an audit log with 8,174 entries. Those are the properties that cannot be added later without rewriting the system, and they are present.

What the audit found instead is a system that was built correctly and then not finished in the operational sense — a throttle written for one login and not the other, a cron file with five routes and one schedule, log tables with no retention, modules switched on for every school before their tables existed. Those are all housekeeping, and housekeeping is cheap.

The single most dangerous category is not a security hole. It is Class E: Payroll and Tahfiz enabled for 14–17 schools, sitting in the sidebar, accepting input into tables that do not exist or are empty. A school will spend a week entering payroll before discovering nothing was saved, and no error will ever have been shown. Fix that first — it costs a configuration change, and it is the only finding here that actively destroys a user's work.

All figures measured against production on 2026-08-10 at commit 674a09d3. Read-only; nothing was modified.

Two limits worth stating: this audit detects missing tables, not missing columns — the finance outage fixed this week was a wrong column in a table that exists, and that class would not appear here. And row counts reflect current adoption, so a module measured as empty is not thereby proven broken.
