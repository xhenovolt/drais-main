# v1.117.0 — Permanent (hard) delete for schools

**Nature:** minor (a guarded, irreversible cleanup action).

Answers: *"why is there no hard delete — I may want to remove a test school
permanently."* There now is one, built so it can clean up a test school but can
never nuke a live one by accident.

## Why it was soft-only until now

A school's data lives across **every tenant table** keyed by `school_id`
(students, staff, attendance events, devices, finance, …). Deleting just the
`schools` row would orphan all of it. So soft-delete (recoverable) was the safe
default; hard-delete needed real guardrails first.

## The guardrails (all enforced server-side)

Permanent delete is refused unless **every** condition holds:

1. **Super-admin** operator.
2. The school is **already soft-deleted** (two-step: delete → then permanently
   delete).
3. The operator **retypes the exact school name**.
4. A **data-heavy school is refused unless `force`** — ≥20 learners, ≥20 staff,
   or ≥500 attendance events trips the guard, so a real school can't be
   fat-fingered away. The UI shows the footprint before you confirm.

## What it does

Discovers every base table with a `school_id` column
(`INFORMATION_SCHEMA`, validated identifiers only), then **in a single
transaction** deletes that school's rows from each, and finally the `schools`
row — rolling back entirely on any error. Returns a per-table row-count summary,
and writes a `school_hard_deleted` audit row (name, footprint, tables, total
rows, whether forced).

## Surfaces

- `POST /api/control-center/schools/[id]` gains `footprint` (preview) and
  `hard_delete` (`{ confirm_name, force }`) actions.
- On a **soft-deleted** school, `/control/schools/[id]` → Lifecycle → a **Danger
  zone** with **Permanently delete**: it shows the footprint, requires typing the
  name, double-confirms + forces for a real school, then removes it and returns
  you to the schools list.
