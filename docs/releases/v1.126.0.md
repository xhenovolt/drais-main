# v1.126.0 — Money wave Phase 15: plan-limit enforcement (safe by default)

**Nature:** minor (E-9). **Final increment of the Money wave.**

## What this adds

Plan limits (learners / staff / devices) now actually **gate usage** at
create-time — so a plan means something and hitting the cap prompts an upgrade,
instead of the limits being purely advisory.

Wired into the primary create paths:

- **Add a learner** (`POST /api/students`)
- **Add a staff member** (`POST /api/staff/add`)
- **Assign a device to a school** (Control device assignment)

When a school is at its plan cap, the action is refused with a clear message:
*"Plan limit reached: 300/300 learners. Upgrade the plan or contact Xhenvolt."*

## Safe by default (this is the important part)

Enforcement is engineered so it can **never blank a live school** by surprise:

1. **OFF unless enabled** — nothing blocks unless `ENFORCE_PLAN_LIMITS=true` is
   set in the environment.
2. **Per-school override** — `school_settings.billing.enforce_limits` = `on` /
   `off` overrides the global either way (a safety valve for a school that's
   legitimately growing past its plan while you sort out the upgrade).
3. **Unlimited / unmanaged always pass** — a `null`/`0` limit or a school with no
   plan is never blocked.
4. **Fails open** — any error in the enforcement path allows the action.

So this release ships the mechanism inert; you flip it on when you're ready, per
school or platform-wide.

## Code + tests

- `src/lib/control/plan-enforcement.ts` — `enforcePlanLimit(schoolId, resource)`
  (reuses the `checkCanAdd` maths) + the **pure** `resolveEnforcement`
  (override-vs-global precedence, 3 unit tests).

No new cron; no schema change.
