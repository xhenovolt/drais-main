# v1.105.0 — Policy-aware Time Health (drift analysis reads the time policy)

**Nature:** minor (a missing capability added — the Time Intelligence engine now
understands the school's device-time policy).

## The problem

Attendance Settings lets a school choose a **device time policy**:

- `CORRECT_BY_DRIFT` — DRAIS realigns drifted punches automatically;
- `TRUST_DEVICE_TIME` — keep the device's own clock, drift and all, by choice;
- `MANUAL_REVIEW_IF_DRIFT` — keep device time but flag drift for a human.

**Time Health was blind to that setting.** Its analysis only ever looked at
`punch_at` (the stored instant) against the learned baseline, so it could not
tell:

- whether `CORRECT_BY_DRIFT` had **already resolved** a real device drift — a
  fixed device just read as a plain "trusted", the save was invisible;
- that under `TRUST_DEVICE_TIME` the drift is retained **on purpose** — yet it
  still flagged an "anomaly" and nagged the operator to shift the batch,
  contradicting the very policy they set;
- when auto-correction ran but **didn't fully land** — it reported "device clock
  wrong" as if no auto-correction existed at all.

The result was wrong / misleading data points, exactly as reported.

## The fix — dual-drift, policy-aware verdicts

The engine now reads two independent signals per device-day:

- **raw device drift** — what the *clock* actually did, taken from the
  `clock_skew_seconds` already recorded at ingest (no re-ingest needed);
- **residual drift** — what remains in the stored `punch_at` after the policy
  ran (the previous single signal).

A new **pure** `applyPolicy()` layer combines those with the active policy:

| Policy | Raw drift | Residual | New verdict |
|---|---|---|---|
| CORRECT_BY_DRIFT | large | ~0 | **"Drift auto-corrected by policy"** — `resolvedByPolicy`, trusted (the previously-invisible good news) |
| CORRECT_BY_DRIFT | large | large | **"Auto-correction incomplete"** — points at enabling device auto-sync |
| TRUST_DEVICE_TIME | large | — | **"Trusted per policy (uncorrected by design)"** — informational, no shift nag; anomaly downgraded to review |
| MANUAL_REVIEW_IF_DRIFT | large | — | **"Flagged for manual review"** — kept pending your decision |
| any | RTC-dead / future stamps | — | unchanged — hard failures still stand under every policy |

## What changed

- `confidence.ts` — `Assessment` gains `rawDriftMin` / `residualDriftMin` /
  `resolvedByPolicy` / `policy`; new **pure** `applyPolicy()` (8 new unit tests,
  20 total passing).
- `engine.ts` — reads `clock_skew_seconds`, computes median raw drift, runs
  `applyPolicy`, persists the new columns; `deviceHealthOverview` now returns the
  active `policy`.
- `schema.ts` — additive `raw_drift_min` / `residual_drift_min` /
  `resolved_by_policy` / `policy` columns on `device_clock_health` (backfilled on
  next sweep).
- Time Health page — shows the **active policy** in the header, an **"Auto-resolved"**
  state (green ShieldCheck) distinct from a plain trusted device, and a **"Device
  clock drift"** metric alongside the residual offset. Full EN + AR (10 new keys,
  parity verified).

## Side effect (good)

The inline logs-page / dashboard time badges consume the same verdicts, so an
auto-resolved drift no longer surfaces as a false anomaly there either.
