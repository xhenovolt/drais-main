# v1.132.0 — Resilience Phase 23: platform maintenance mode + deploy safety

**Nature:** minor (E-20). Makes risky deploys/migrations safe, and documents the
rollback strategy. **Completes the automation & resilience wave.**

## Maintenance mode

A platform switch (System Health → Maintenance mode), super-admin, three levels:

- **Off** — normal.
- **Banner** — a full-width notice to every school (custom message); full access.
- **Read-only** — the notice **plus tenant writes are blocked** (mutating
  requests through `withRoute` return `503 Retry-After`); reads still work.

The **Control Center is never blocked**, so an operator can always lift it. The
flag is cached 30s, so it adds no per-request DB cost on the hot path.

- School app shows a top **maintenance banner** (polls `/api/platform/maintenance`).
- `GET/POST /api/control-center/maintenance` (set; audited `maintenance_set`);
  public `GET /api/platform/maintenance` drives the banner.

## Deploy safety / rollback strategy (documented)

- **Before a risky deploy/migration:** set **Read-only** (or Banner) → deploy →
  verify → set **Off**.
- **Rollback:** every release is a git tag; redeploy the previous tag to roll
  back. Runtime schema changes are **additive only** (never destructive), so a
  rollback is safe against the current DB.
- **Upgrade strategy:** additive migrations via runtime schema-ensure; new
  columns/tables are backward-compatible with the prior deploy.

## Code + tests

- `src/lib/control/platform-settings.ts` — KV store + `getMaintenance`

No new cron; additive schema.
