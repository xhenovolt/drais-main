# v1.110.0 — Subscription plan engine (Roadmap P5)

**Nature:** minor (a real plan catalog replaces free-text plan strings).

## What this closes

Defect #7 / founder-dependence F-2: the platform had **no real subscription
engine** — `set_subscription` wrote a free-text plan name with no meaning and no
limits. Now there is a proper catalog of tiers with configurable resource limits,
assignable from the Control Center, with live usage shown against them.

## Plan catalog

A new `subscription_plans` table, seeded with five preset tiers (edit or extend
freely; **Custom** is created ad-hoc):

| Plan | Learners | Staff | Devices | SMS/mo | Storage |
|---|---|---|---|---|---|
| Starter | 300 | 30 | 1 | 500 | 2 GB |
| Standard | 800 | 80 | 2 | 2 000 | 5 GB |
| Professional | 2 000 | 200 | 5 | 10 000 | 20 GB |
| Enterprise | ∞ | ∞ | 20 | 50 000 | 100 GB |
| Government | ∞ | ∞ | ∞ | ∞ | ∞ |

A `null`/`0` limit means **unlimited**. Each plan also carries a feature list.

## Surfaces

- **`/control/plans`** — the catalog, with inline editing of every limit
  (super-admin, audited via `plan_saved`).
- **`/control/schools/[id]` → Plan & usage panel** — the school's current plan,
  an **Assign plan** dropdown, and live **usage bars** (learners / staff /
  devices) vs the plan limits, with an OVER flag when a resource exceeds the cap.
- `GET/POST /api/control-center/plans` (list / upsert) and a new
  `assign_plan` action on `POST /api/control-center/schools/[id]`.

A school links to a plan through the **existing** `schools.subscription_plan`
column (now holding the plan code), so no tenant-schema change was needed.

## Code + tests

- `src/lib/control/subscriptions.ts` — catalog CRUD (`listPlans`, `upsertPlan`,
  `getPlanByCode`, `assignPlanToSchool`), `schoolUsage`, and the **pure**
  `usageAgainst` / `checkCanAdd` limit maths (6 unit tests; 22 control tests
  total). Enforcement rules live in `checkCanAdd` now so create-time enforcement
  can adopt them without re-deriving.

## Roadmap

Closes **P5** (the catalog + assignment + usage visibility). A focused follow-up
(**P5.1**) can wire `checkCanAdd` into the learner/staff/device create paths to
*hard-enforce* limits. Remaining: **P6 — school lifecycle**, **P7 — UX +
theming**, **P8 — console security hardening**.
