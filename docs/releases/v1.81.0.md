# DRAIS v1.81.0 — Attendance Health Center

**Attendance Intelligence Program · Phase 1** (baseline: `docs/audits/ATTENDANCE_ARCHITECTURE_AUDIT.md`)

## Release notes

One page — **/attendance/health** (sidebar → Attendance → Health Center) — answers *"is attendance OK right now?"* without SQL:

- **Overall Attendance Health Score** (weighted 0–100: Healthy ≥90 / Degraded ≥70 / Needs attention <70)
- **Ten live pipeline checks**, each a card with score, status, plain-language detail and a concrete recommendation:
  device connectivity · heartbeats · attendance flow (today's volume vs the school's learned normal) · time synchronization (Time Intelligence) · SMS health · identity mapping · notification queue · background jobs (stalled pulls) · database latency · device clock reputation (30d)
- **Recommendations ranked worst-first** — each names the page/action that fixes it
- **Live refresh** every 30s (toggleable) + manual re-check
- **Health API**: `GET /api/attendance/health` (session-scoped; any authenticated school user)

First live run against JIPRA surfaced three genuine findings (stalled acquisitions, unmatched punches, DB latency) — the page pays for itself on day one.

## Database changes

**None.** All checks read existing tables (`devices`, `attendance_raw_events`, `attendance_time_baselines`, `device_clock_health`, `notification_outbox`, `attendance_acquisitions`). No migrations, no new tables.

## API changes

- **Added** `GET /api/attendance/health` → `{ score, status, checks[], recommendations[], generated_at }`. Additive; no existing endpoint touched.

## Architecture notes

- `src/lib/attendance/health.ts` — `runHealthChecks(schoolId)` (each check individually guarded; a failing probe reports itself as `unknown` and is excluded from the score) + **pure** `computeOverallHealth()` (unit-tested).
- Reuses Phase 4-era Time Intelligence outputs (`device_clock_health`, baselines) rather than re-deriving them.
- No cron: checks run on request, same pattern as every DRAIS sweep.

## Risk analysis

- Read-only feature — cannot corrupt data.
- Worst case: the endpoint is slow on huge schools (10 sequential-ish queries). Each is indexed; measured ~1s on JIPRA including a 348ms base RTT.
- Score thresholds are heuristics; they may need per-school tuning in later phases (settings hook planned).

## Rollback plan

Revert the release commit (`git revert`) — no schema to unwind, no data written. The page/API disappear cleanly; nothing else references them.
